xa11y normalizes platform-specific APIs into a unified interface. This page documents how roles and actions map across platforms, and where behavior differs.

Roles not recognized by a platform map to `Unknown`.

A password field keeps the `TextField` role and sets the `password` state
instead: `AXSecureTextField` as the role or subrole on macOS, the
`password text` role on Linux, and `IsPassword` on Windows. xa11y does not
redact a password field's value or the text typed into it: the value is
whatever the platform reports. On Windows, a password control may decline to
report its value (a WPF `PasswordBox` does), and its `value` is then `None`.
The Win32 edit control's provider reports a placeholder, `Access denied`, in
place of the text, and xa11y passes that placeholder through.

## Action mapping

| xa11y Action | macOS | Linux (AT-SPI) | Windows (UIA) |
| --- | --- | --- | --- |
| `Press` | AXPress *(AXOpen when the element has AXOpen and no AXPress)* | click, activate, press, invoke | InvokePattern, TogglePattern, SelectionItemPattern, or ExpandCollapsePattern. LegacyIAccessible.DoDefaultAction only for an element with none of those and a non-empty MSAA default action |
| `Focus` | set AXFocused=true | Component.GrabFocus | SetFocus |
| `Blur` | set AXFocused=false | *(not directly supported)* | *(not directly supported)* |
| `Toggle` | AXPress *(on checkbox)* | toggle, check, uncheck | TogglePattern |
| `Expand` | AXShowMenu / AXPress | expand, open | ExpandCollapsePattern.Expand |
| `Collapse` | AXCancel / AXPress | collapse, close | ExpandCollapsePattern.Collapse |
| `Select` | AXPress | select | SelectionItemPattern |
| `SetValue` | set AXValue attribute | Value.SetCurrentValue (numeric) / EditableText.ReplaceText (text) | RangeValuePattern / ValuePattern |
| `TypeText` | set AXSelectedText | EditableText.InsertText | ValuePattern *(splice)* |
| `SetTextSelection` | set AXSelectedTextRange | Text.SetSelection | TextPattern range ops |
| `Increment` | AXIncrement | increment *(or Value +step)* | RangeValuePattern *(+step)* |
| `Decrement` | AXDecrement | decrement *(or Value -step)* | RangeValuePattern *(-step)* |
| `ShowMenu` | AXShowMenu | menu, showmenu, popup | ExpandCollapsePattern |
| `ScrollIntoView` | AXScrollToVisible *(when advertised)* | Component.ScrollTo | ScrollItemPattern |

On Windows, the MSAA default action stands in for `Press` only on an element served through MSAA, where the UIA `FrameworkId` is `Win32`, `WinForm`, or empty. Native UIA providers such as Chromium keep their own choice. Each Windows element's `raw` map lists the UIA activation patterns it has under `uia_activation_patterns`, and its provider under `uia_framework_id`. Event targets include these properties too.

Window verbs map differently again, because each platform's window control
API is separate from its element-action interface:

| xa11y Action | macOS | Linux X11 | Linux Wayland (Sway) | Windows (UIA) |
| --- | --- | --- | --- | --- |
| `Activate` | activate app, restore if minimized, then AXRaise | `_NET_ACTIVE_WINDOW` | Sway `focus` | restore if minimized, then SetForegroundWindow (verified with GetForegroundWindow, up to 3 tries; fails if the window is still not in front) and SetFocus |
| `Minimize` | clear AXFullScreen when fullscreen, then set AXMinimized=true | ICCCM `WM_CHANGE_STATE(IconicState)` | unsupported | WindowPattern.SetWindowVisualState(Minimized) |
| `Maximize` | unsupported | `_NET_WM_STATE_MAXIMIZED_HORZ` + `_VERT` | unsupported | WindowPattern.SetWindowVisualState(Maximized) |
| `EnterFullscreen` | set AXFullScreen=true | `_NET_WM_STATE_FULLSCREEN` | Sway `fullscreen enable` | unsupported |
| `Restore` | clear AXMinimized; set AXFullScreen=false | map and remove fullscreen/maximized EWMH states | Sway `fullscreen disable` | WindowPattern.SetWindowVisualState(Normal) |
| `Close` | press the AXCloseButton | `_NET_CLOSE_WINDOW`; ICCCM `WM_DELETE_WINDOW` when the window manager does not advertise it | Sway `kill` | WindowPattern.Close |
| `MoveTo` | set AXPosition | `_NET_MOVERESIZE_WINDOW` | Sway `move position` for floating windows | TransformPattern.Move |
| `ResizeTo` | set AXSize | `_NET_MOVERESIZE_WINDOW` | Sway `resize set` for floating windows | TransformPattern.Resize |

`Maximize` and `EnterFullscreen` are distinct operations, not two names for
one state: macOS has no accessible `maximize` (see below) and Windows has no
fullscreen accessibility API, so each platform advertises only the operation
it can actually perform.

Window state reads follow the same split. `minimized`, `maximized`, and
`fullscreen` are `Option<bool>`: `None` means *unknown*, either because the
element is not a window or because the platform cannot report the state.
macOS reads `minimized` and `fullscreen`
(`AXMinimized` / `AXFullScreen`) on window-like elements; there is no AX
attribute for the zoom state (`AXZoomed` is not declared in the SDK, and live
windows answer `kAXErrorAttributeUnsupported` for it), so `maximized` is
always `None` on macOS. Entries into native fullscreen report through
`fullscreen`. Windows reads `minimized` and `maximized` from
`WindowPattern.CurrentWindowVisualState` but cannot report `fullscreen`;
Linux X11 reads all three states from `_NET_WM_STATE`. Sway reports
`fullscreen`; `minimized` and `maximized` stay unknown because Sway has no
such states. Other Wayland compositors retain the AT-SPI `ICONIFIED` reading
for `minimized` and leave the other states unknown. `modal` is
`WindowPattern.CurrentIsModal` on Windows and `AXModal` on macOS.

An advertised window verb means the current native backend reported support
and the accessibility target resolved to one native window. A missing verb is
unsupported or unresolved for that snapshot. A direct call returns
`Unsupported` with the missing capability or identity reason. Window states
are tri-state: `Some(true)` and `Some(false)` are observed values, while
`None` is unknown.

Linux snapshots also expose `raw.window_capabilities`, with one of
`supported`, `unsupported`, or `unknown` for each window verb. `unknown` means
no native backend or reliable identity was available. `raw.window_backend`
names the provider when resolution succeeded (`x11-ewmh`, `x11-icccm` when
no X11 window manager is running, or `wayland-sway-wlr-foreign-toplevel`). These raw fields are diagnostic; the
portable dispatch contract remains the `actions` list plus the method error.
On Sway, `raw.window_protocol_version` records the advertised wlr protocol
version used for capability detection.

X11 and Sway success means the native request was accepted for delivery. The
window manager applies requests asynchronously, so callers that require an
observed postcondition should fetch a new snapshot and wait for the state or
bounds. A compositor refusal or stale target is an error, as is ambiguous identity.
Maximized and fullscreen remain separate states. `Restore` clears every state
that the selected backend can represent.

## Platform caveats

### ScrollIntoView

On macOS it performs `AXScrollToVisible` when the element advertises that action, and returns `ActionNotSupported` otherwise. On Linux it uses `Component.ScrollTo` with top-edge alignment. On Windows it uses `ScrollItemPattern.ScrollIntoView`.

### Activate: AXRaise alone does not activate

`AXRaise` on a window only re-raises the window within the window list of its
own app, and it answers success even while the app sits in the background. An
activation performed on a background app's window visibly does nothing.
`Activate` on macOS brings the app forward first (sets `AXFrontmost` on the
application element), then raises the window. A failure to activate is a
surfaceable error, never a silent success.

### `EnterFullscreen`: native fullscreen on macOS

macOS exposes native fullscreen through the `AXFullScreen` attribute, the
only window state the platform both reads and writes. `EnterFullscreen`
sets that attribute to `true`, and `Restore` sets it back to `false`. Because
an already-fullscreen window keeps advertising `enter_fullscreen` whether or
not `AXFullScreen` is settable, a repeated call stays a no-op. When the
window is not fullscreen and cannot be set fullscreen, the verb reports
`ActionNotSupported` instead of succeeding silently.

`Maximize` is a separate operation and is **not supported on macOS**. The
classic zoom state has no readable or writable accessibility surface:
`AXZoomed` is unsupported, and the green button's `AXPress` / `AXZoomWindow`
actions are toggles with no readable state. The provider refuses the verb
with `Unsupported` and never advertises it. Substituting fullscreen
for a `maximize` request would blur two distinct operations. Windows is the
reverse: `Maximize` drives `WindowVisualState_Maximized`, while
`EnterFullscreen` is unsupported because UIA has no fullscreen surface.

The fullscreen transition is asynchronous, and macOS reports transient values
while it runs: a window entering fullscreen can briefly read
`AXFullScreen=false`, and a set issued mid-transition is discarded rather
than queued. The provider polls the window's fullscreen state and re-issues
the absolute set until the promised state holds. A transition that never
commits fails with a timeout error rather than reporting success. A window
that is not fullscreen and whose `AXFullScreen` is not settable has no
fullscreen state to settle: `Restore` clears `AXMinimized` only and returns
without polling. A window that reads fullscreen but cannot clear the state
does not advertise `restore` at all.

`Minimize` on a fullscreen window leaves fullscreen first. AppKit ignores a
minimized set while the window is fullscreen, so issuing it directly would
report success while the window stayed fullscreen. The provider settles the
fullscreen exit first, then applies the minimized state. That is what makes a
back-to-back `enter_fullscreen` → `minimize` → `enter_fullscreen` →
`minimize` sequence land every step.

Leaving fullscreen is `Restore`, not a verb of its own. macOS has a real
"Exit Full Screen" command, but no distinct accessibility operation behind
it. The green button's actions are toggles, and the only absolute exit is the
same `AXFullScreen=false` write that is the inverse of `EnterFullscreen`.
`Restore` performs that write, as well as `AXMinimized=false`, which makes it
the inverse of every entry verb. A separate `exit_fullscreen` verb would be a
second name for the same operation, advertised next to `restore` on the same
window. Minimized, maximized, and fullscreen are mutually exclusive on macOS:
a fullscreen window cannot be minimized, and entering fullscreen brings the
window back from the Dock first. `Restore` has one effect from any state.

### `MoveTo` and `ResizeTo`: verified geometry on macOS

Setting `AXPosition` or `AXSize` succeeds when the window receives the
request, not when the window applies it. Some toolkits apply the write later
or drop it while the window settles from another transition. The window
server also keeps a window inside the screen's visible frame, so it refuses a
size that would extend past it, such as growing a window that already fills
the display's height. The app can refuse a size outside its own minimum or
maximum too.

So the macOS provider reads the attribute back after the write and re-issues
the same absolute value until the window reports the requested geometry,
within 2 points, for up to 5 seconds. If the window never gets there, the
call fails with a timeout error whose diagnosis names the requested geometry
and the geometry the window last reported. A `ResizeTo` error also gives the
window's origin. The verb never returns success for a window that kept its
old frame.

### SetValue: text vs numeric

- **macOS** sets the `AXValue` attribute directly, which works for both text and numeric values.
- **Linux** has a `Value` D-Bus interface that only supports `f64`, so text values require `EditableText.ReplaceText`. If neither interface is available, the call returns `TextValueNotSupported`.
- **Windows** tries `RangeValuePattern` for numeric values and falls back to `ValuePattern.SetValue` for text.

### TypeText

Text is inserted through the accessibility API. Keyboard events are never simulated.

- **macOS** sets `AXSelectedText`, replacing the selection or inserting at the cursor.
- **Linux** calls `EditableText.InsertText` at the current caret offset.
- **Windows** reads the current value via `ValuePattern`. It then splices in the new text and calls `SetValue`.

### Blur

- **macOS** sets `AXFocused` to false on the element.
- **Linux and Windows** have no direct API equivalent, so the action is unsupported.

### Unresponsive apps (macOS)

When the provider is created, xa11y sets the process-wide accessibility messaging timeout to 2 seconds per message, in place of the system default. The setting applies to every accessibility call the host process makes, including ones that don't go through xa11y. A read or action on an app that doesn't answer in time fails with `Error::Platform` carrying `kAXErrorCannotComplete` (-25204). The message names the app's PID, and for actions the app's name too. The message says whether the call ran out the timeout or was refused sooner. A timed-out action may still take effect once the app catches up.

### Text input simulation (Windows)

`InputSim.type_text` submits each Unicode character through `SendInput`,
keeping UTF-16 surrogate pairs in the same submission. It waits at least
10 ms after every character or Enter tap, including the last one, so
consecutive calls retain the same pacing. Typing 100 letters adds at least
one second of delay. The pacing addresses queued Unicode packet corruption
in WPF. The call blocks during these delays.

### Coordinates

Bounds use desktop coordinates with origin at the top-left of the primary display. Windows uses physical pixels. macOS and Linux use logical points where available. Use the screenshot coordinate methods to map bounds onto captured pixels. Note:

- **macOS** reports in points, its native logical unit. On Retina displays, 1 point = 2 physical pixels.
- **Windows** reports physical desktop pixels for bounds, input points, window moves and sizes, and capture regions. `Screenshot.scale` is `1.0`. A window crossing a display seam has continuous bounds and its center remains inside the window, regardless of each display's DPI scaling. Windows DIP coordinates stored by older code need converting to physical desktop pixels first. xa11y asks for Per-Monitor-V2 DPI awareness for the process when it first starts. A host that already chose system-aware or unaware keeps its choice. Each xa11y call that reads coordinates then switches its own thread to Per-Monitor V2 for the duration of the call and back afterwards. Without that, a system-aware host would see scaled coordinates on any monitor whose DPI differs from the system DPI. A host thread that is a single-threaded COM apartment may dispatch its own window procedures while xa11y waits on a COM call. Those procedures inherit the Per-Monitor V2 setting.
- **Linux** reports logical pixels where the HiDPI scale is reliably detectable, and falls back to physical at scale `1.0` otherwise. See [Coordinates and HiDPI](/reference/platform-details/#coordinates-and-hidpi) for exactly when.
- Multi-monitor setups can produce negative coordinates for displays positioned left of or above the primary.

### Name resolution

Platforms use different attributes to determine an element's `name`:

- **macOS** uses AXTitle, then AXDescription, then AXValue (for text elements).
- **Linux** uses Accessible.Name, then Description. For `StaticText` with no name, the first portion of the value is used.
- **Windows** uses the CurrentName property.

### Application nodes (Windows)

UI Automation has no `Application` accessible. Processes surface only as
their top-level windows, so xa11y-windows *synthesizes* one `Application`
node per process (the unified shape every platform reports), with the
process's windows as its children. The node carries no bounds (UIA has no
process geometry) and no window actions or window-state flags. Its handle
is a tagged synthetic identifier and backs no live UIA element, so acting
on the app node itself is refused with `ActionNotSupported` (the core role
guard rejects it before any provider is reached, on every platform);
enumerate the windows and act on a window child instead. The handle is
not PID-encoded: the PID is the node's `pid` field, and the handle itself
is a per-run counter tagged as synthetic.

The node's `raw` map records how it was built:

| raw key | Value |
|---|---|
| `uia_synthesized` | `true`. The marker for a node that was synthesized and backs no live UIA element. |
| `uia_name_source` | `"package"` (a packaged app's display name, as the Start menu shows it), `"process"` (executable stem from `OpenProcess` + `QueryFullProcessImageNameW`), or `"window_title"` (the representative window's title, used when the process cannot be opened) |
| `uia_process_name` | full executable path, when the process could be queried |
| `uia_app_user_model_id` | the AppUserModelID of a packaged app's process |

The representative window is the process's first top-level window in z-order.

A packaged app (UWP, or a packaged desktop app) takes the display name the Start menu and taskbar show, so Calculator is `Calculator` rather than `CalculatorApp`. xa11y reads the process's AppUserModelID and asks the shell for that app's entry in `shell:AppsFolder`, which resolves the manifest's localized `DisplayName`. This also applies to desktop apps installed as packages. On Windows 11 the Notepad node is `Notepad` and the Windows Terminal node is `Terminal`, where earlier versions of xa11y used the executable names `notepad` and `WindowsTerminal`. A packaged app with no Start-menu entry keeps its executable name, and `uia_name_source` says which one the node got. Apps that aren't packaged keep the executable name.

UWP and other packaged apps draw inside a frame window that `ApplicationFrameHost.exe` owns. xa11y attributes that frame to the app it shows, so each app has its own name and process ID. A running app's frame is matched through the app's own `Windows.UI.Core.CoreWindow` inside it. A minimized or suspended app's frame is matched by its AppUserModelID to the process that has the same one. A frame whose app has exited belongs to no app: it is left out of the list, and an app lookup that fails names it in its diagnosis.

xa11y sets the UIA connection timeout to 2 s and the transaction timeout to 20 s, so one hung provider cannot stall a call for longer than that. A window Windows already reports as not responding (`IsHungAppWindow`) fails fast instead. Listing apps, looking an app up by process ID, reading an app's windows, and finding the foreground app all return `Timeout`, and the diagnosis names each hung window with its title, process ID and executable. The elapsed time on that `Timeout` reports the 5 s threshold Windows uses to call a window hung. xa11y itself does not wait. A window that is only briefly busy is read normally.

Discovery operations also turn a UIA call that runs out either timeout into `Timeout`. UIA returns the same `UIA_E_TIMEOUT` for both limits. The error's elapsed time is how long the call took, and its diagnosis names the limit that fits. UIA doesn't say which window the app listing failed to reach. On that failure the listing probes each visible top-level window with a `WM_NULL` message, bounded at 250 ms per window and 2 s overall. The windows that time out become the diagnosis candidates. Calls on a single element still report `UIA_E_TIMEOUT` as `Platform`.

A window that stopped answering less than 5 s ago is not hung yet by the operating system's rule. When the desktop query in UIA reaches such a window, it waits out its timeouts and succeeds with the window left out. To catch that, the app listing compares the windows UIA returned with the visible top-level windows that `EnumWindows` reports. An owned window, such as a dialog, counts as returned when its owner was, because UIA lists it under the owner. Only the missing ones get a `WM_NULL` probe. A missing window that doesn't answer fails the listing with `Timeout`. Its diagnosis names the window, and the elapsed time is how long the UIA query took. If a missing window answers the probe, it changed during the listing or is an app window with no name yet, so the listing succeeds with a line on stderr naming it. The same holds when Windows refuses the probe outright, as with an elevated window.

Windows subscriptions register their UIA handlers on every current top-level
window of the process, and a desktop-scoped open/close watch attaches windows
opened after `subscribe` (and drops closed ones, so a closed window stops
producing state deltas). Events from sibling windows follow the
same "the process" semantics as the main window.

### Checked state

The tri-state checked value (`Off` / `On` / `Mixed`) is derived differently:

- **macOS** parses the `AXValue` attribute, where `"0"` = Off, `"1"` = On, `"2"` = Mixed.
- **Linux** uses the AT-SPI state bits `Checked` (0x10) and `Mixed` (0x2000).
- **Windows** reads `TogglePattern.CurrentToggleState`, where 0 = Off, 1 = On, 2 = Indeterminate. Any other value reads as `None`, because the state is unknown. A failed read returns a `Platform` error and is never reported as `Off`.

### Visible state and bounds (Linux)

On Linux, `visible` requires the AT-SPI `Showing` state as well as `Visible`. `Visible` alone means the object would be drawn if its ancestors were. Rows scrolled out of a list, widgets in a hidden page, and the contents of a minimized window keep `Visible` but lose `Showing`, so xa11y reports them as not visible. So an auto-wait on `visible` waits for the element to be on screen.

`bounds` is `None` when `Component.GetExtents` reports a sentinel instead of a position: an `INT32_MIN` coordinate (unrealized GTK widgets), a negative size, or `0x0`. A zero width or a zero height alone, such as a separator line, is still reported, matching Windows.

GTK 4 apps need different handling. GTK 4 doesn't know where its window is, and its screen extents are `(0, 0)` or window-relative wherever the window sits. For a GTK 4 app on X11, xa11y computes `bounds` as the widget's window-relative extents plus the X11 origin of its top-level window. It finds that window by process id and exact title, never by geometry. The origin is cached until the window moves, is renamed, or another top-level appears or goes away. When the title matches no window or several, `bounds` is `None` rather than a wrong position. `bounds` is also `None` when xa11y cannot read the app's toolkit name and version, since raw screen extents might be GTK 4's.

Whenever the Wayland window backend is selected, GTK 4 `bounds` are always `None`, because a Wayland client has no global position. That includes a GTK 4 app forced onto XWayland with `GDK_BACKEND=x11`. The window-relative extents are assumed to be in the same pixels as the X11 window origin. This is correct at scale 1. xa11y has not verified it under `GDK_SCALE=2`.

### Visible state (Windows)

On Windows, `visible` starts from the UIA `IsOffscreen` property, which some providers leave false on content that can't be seen. xa11y corrects two cases:

- The contents of a minimized window are not visible.
- An item that lies entirely outside the bounds of an ancestor whose content overflows is not visible, while one partly inside still counts as visible. "Overflows" means the ancestor's UIA Scroll pattern says it can scroll horizontally or vertically, so a custom scrolling control with no Scroll pattern isn't covered.

The scroll check has limits. UIA has no viewport rectangle, so the ancestor's bounds stand in for it, and an item hidden only behind a scroll bar or header still counts as visible. A popup or top-level window, such as an open drop-down list, isn't clipped by anything above it, because it's drawn over its owner's content. Event targets skip the scroll check, so a scrolled-out item can report visible on an event. Each element's `raw` map carries `uia_is_offscreen`, the UIA value before these corrections.

Auto-waiting actions wait for `visible`, and scroll a control that is only scrolled out into view first (see the [locator reference](/reference/locator/#locator)). That scroll, like `scroll_into_view()` itself, needs the UIA ScrollItem pattern, which list items, tree items and similar controls have. A plain control such as a button has none: the call returns `ActionNotSupported`, and an action on a scrolled-out button times out with a diagnosis that says the scroll was refused. For those, call `focus()` on an `Element` snapshot, because frameworks such as WinForms scroll a focused control into view. `Locator.focus()` doesn't help there, because it also waits for `visible`.

An item under a collapsed parent that also lies outside a scrolling ancestor's bounds reads `scrolled_out`, because the scroll check runs before `IsOffscreen` is consulted. Scrolling doesn't reveal it: ScrollItem accepts the call and the item stays hidden until its parent expands. The auto-wait stops calling it after three accepted calls, and its timeout says the item stayed scrolled out. Expand the parent first.

### Hidden reason

When `visible` is false, `hidden_reason` says why, and it is `None` (`null` in JavaScript) whenever `visible` is true. When more than one reason applies, the first in this table wins:

| Value | Meaning |
| --- | --- |
| `window_minimized` | The element's window is minimized. Restore it to act. |
| `scrolled_out` | An ancestor that scrolls has moved the element out of its viewport. Scroll it into view to act. |
| `not_showing` | The platform reports the element hidden for a reason it doesn't name, such as a collapsed section or a hidden page. |
| `unknown` | The element is hidden, and xa11y couldn't tell which of the reasons above applies. |

What each platform can tell apart:

- **Windows** reports `window_minimized` for the contents of a minimized window and `scrolled_out` for the scroll check described above. `IsOffscreen` alone gives `not_showing`.
- **Linux** reads the reason from AT-SPI states and, where those don't settle it, from the element's ancestors:
  - The `Iconified` state, on the element or on an ancestor climbed past, gives `window_minimized`.
  - For an element that keeps `Visible` but lacks `Showing`, xa11y climbs to the nearest ancestor that is showing. The reason is `scrolled_out` only when the element lies outside that ancestor's extents and one of the ancestors climbed is a scrolling container: `list`, `list box`, `scroll pane`, `table`, `tree`, `tree table`, or `viewport`. Lying outside a container that doesn't scroll gives `not_showing`.
  - An element without `Visible` reports `not_showing`, with one exception. An item cell (`list item`, `table cell`, `table row` or `tree item`) that lies outside a showing scrolling container that is its parent reports `scrolled_out`, because Qt clears `Visible` on a row scrolled out of its view.
  - A read that fails during these checks gives `unknown`, and so does a failed read of the element's own bounds or state set. Event targets skip the ancestor walk and report `unknown` for the `Visible`-without-`Showing` case.
  - GTK 4 keeps `Visible` and `Showing` on widgets scrolled out of a `GtkScrolledWindow`, so they read as visible.
  - The auto-wait's scroll is `Component.ScrollTo`. Qt has no `ScrollTo`, so `scroll_into_view()` on a Qt row returns `ActionNotSupported`, and an action on a scrolled-out Qt row times out with a diagnosis that says the scroll was refused. A `false` reply from `ScrollTo` counts as a refusal too.
- **macOS** has only `AXHidden`, which carries no reason, so every hidden element reports `not_showing`.

A timeout on an element that matched but stayed hidden carries the reason in its diagnosis. See [errors](/reference/errors/).

### Delivery disposition

Each failed action reports `not_delivered` or `unknown`. See [errors](/reference/errors/#delivery-disposition) for the values. A failure is `not_delivered` only when the backend decided it before it called the application. Every platform error from the dispatching call stays `unknown`.

| Platform | `not_delivered` | `unknown` |
| --- | --- | --- |
| Linux | The element lists no matching AT-SPI action or lacks the interface the verb needs (`ActionNotSupported`). The object or its peer is gone before dispatch (`ElementStale`). `GrabFocus` (behind `focus` and `activate`) answers `false` or D-Bus `NotSupported`, because the adapter declined to take focus and focusing twice is harmless. Bad arguments or an unsupported session. | A D-Bus method timeout (`Timeout`). A failed `DoAction`, `SetCurrentValue`, `SetTextContents` or `Select*`. `DoAction` returning `false`, because a provider that acts and then returns `false` looks the same as one that declined. A window-manager request that was sent and not confirmed. |
| macOS | `kAXErrorActionUnsupported` (`ActionNotSupported`). Role and attribute checks made by xa11y itself. Stale handles and bad arguments. | `kAXErrorCannotComplete`, which is also what an expired messaging timeout surfaces as. Every other AX code from the dispatching call, including `kAXErrorInvalidUIElement`. A window verb that did not settle in its budget (`Timeout`). |
| Windows | Pattern acquisition answers `E_NOINTERFACE`, `UIA_E_INVALIDOPERATION` or an empty error (`ActionNotSupported`). `ValuePattern.SetValue` answers `UIA_E_INVALIDOPERATION` for a read-only control (`TextValueNotSupported`). The handle is not in the cache or no longer matches its identity (`ElementStale`). Bad arguments. | `UIA_E_TIMEOUT` from an element-level call. Every other HRESULT, including `UIA_E_NOTSUPPORTED` and `UIA_E_ELEMENTNOTAVAILABLE`, from the pattern call that performs the action. |

These rules hold on every platform:

- A verb that works in several steps reports `unknown` for a failure after its first step went through, even when the failing step alone would say `not_delivered`. Linux `set_value` can fail on `InsertText` after `DeleteText` emptied the field, and the X11 `minimize`, `maximize` and `enter_fullscreen` send two or three window-manager messages. On macOS the same holds for `minimize`, `enter_fullscreen`, `restore`, `activate` and `resize_to`.
- Input simulation reports a platform failure as `unknown`. A chord can fail after a modifier was already pressed, and the input backends do not tell that apart from a failure of the first event.
- A `Timeout` raised by xa11y's own wait or auto-wait reports `not_delivered`, because the wait expired before the action was attempted. A `Timeout` raised by a backend while it talks to the platform, such as a D-Bus `NoReply` or a stalled discovery call, reports `unknown`, because the backend cannot say whether it came before or after dispatch.

### Selected state

Per-item selection (`selected` on rows, cells, list items) is read differently:

- **macOS** uses the per-element `AXSelected` attribute when present. Some bridges (Qt's among them) provide no per-element `AXSelected` and expose selection only through the container's `AXSelectedChildren`. For `table_cell` / `table_row` / `list_item` elements whose `AXSelected` attribute is absent, xa11y resolves `selected` by membership in the nearest ancestor's `AXSelectedChildren` (at most two hops: cell → row → table). Derived values appear in `states.selected` alone, and `raw` never gains a synthetic `AXSelected` key.
- **Linux** uses the AT-SPI `Selected` state bit.
- **Windows** uses `SelectionItemPattern.CurrentIsSelected`.

### Table headers

Header exposure varies by toolkit as well as platform. Windows surfaces header cells as `HeaderItem` elements and per-cell header relationships via the `TableItem` pattern. AT-SPI exposes `column header` / `row header` roles. AppKit tables expose a header group whose sort buttons carry the column titles. One known toolkit gap: **Qt tables on macOS expose no header objects at all**. Qt's Cocoa bridge synthesizes `AXRow`/`AXColumn` children only and provides no `AXHeader` attribute, so column titles are absent from the AX tree and xa11y cannot surface them. This is an upstream Qt limitation. Use the platform-consistent `table table_cell` selectors for data, and avoid depending on header names for Qt apps on macOS.

### Linux: X11 vs Wayland

xa11y supports both X11 and Wayland Linux sessions. Backends are selected at runtime, with no compile-time feature flag.

| Capability | X11 | Wayland |
| --- | --- | --- |
| Accessibility (AT-SPI2) | D-Bus, no display-server dependency | D-Bus, no display-server dependency |
| Input simulation | `XTest` extension (no setup) | `/dev/uinput` virtual evdev device (requires the `input` group or a udev rule) |
| Screen capture | `GetImage` on the root window | PNG URI from `org.freedesktop.portal.Screenshot` |
| Window management | EWMH/ICCCM | Sway native IPC, gated by `zwlr_foreign_toplevel_manager_v1` |

Auto selection uses these rules independently for input, screenshots, and
window management:

- A usable `XDG_SESSION_TYPE` identifies the desktop session.
- When both display variables are present, xa11y selects Wayland because
  `DISPLAY` names the XWayland compatibility endpoint in that configuration.
- A stale session type falls back to the live endpoint.
- No endpoint returns an `Unsupported` error that explains the missing endpoint.

Set `XA11Y_LINUX_INPUT_BACKEND`, `XA11Y_LINUX_SCREENSHOT_BACKEND`, or
`XA11Y_LINUX_WINDOW_BACKEND` to `x11` or `wayland` for an explicit route.
`auto` restores detection. Each override is independent, and a missing
endpoint is an error instead of a fallback to another backend.

#### Native window identity and support

X11 resolves AT-SPI windows against `_NET_CLIENT_LIST`. With no window manager
running, as on a bare Xvfb display, nothing maintains that list, so xa11y
resolves against the root window's mapped, non-override-redirect children,
which ICCCM defines as the top-level windows. Either way it requires an exact
`_NET_WM_PID` match. For a process with multiple windows, live frame geometry
and then the title narrow the candidates within that PID. Title is never identity on its own.
Every action resolves again, which catches destroyed windows and XID reuse.

The initial native Wayland backend targets Sway. It requires Sway's IPC socket
and the compositor's advertised wlr foreign-toplevel protocol. The wlr
protocol has no PID or accessibility identifier, so xa11y uses the Sway tree
to prove PID-backed identity and to issue the compositor request. That tree
contains native Wayland and XWayland toplevels, and duplicate candidates fail
as ambiguous. Other compositors such as GNOME and KDE Plasma currently report
native window actions as unsupported. They do not receive simulated shortcuts.

Sway supports activation, fullscreen entry and exit, and close. Its model has
no minimized state or maximized state distinct from fullscreen. Move and resize
are advertised only for floating containers. X11 capabilities come from the
window manager's `_NET_SUPPORTED` list.

X11 `Close` picks its mechanism before sending anything. When
`_NET_SUPPORTED` lists `_NET_CLOSE_WINDOW`, the window manager receives that
request. Otherwise, when the window's `WM_PROTOCOLS` lists `WM_DELETE_WINDOW`,
xa11y sends the client the `WM_DELETE_WINDOW` message that a window manager
would forward. That message is a polite request the app may answer with a
save prompt. When neither applies, `close` is not advertised and a direct call
returns `Unsupported` naming both missing capabilities. xa11y never retries a
failed request through the other mechanism, and never force-closes a client
with `XKillClient`. Without a window manager, `close` is the only X11 window
verb, and the window states read as unknown. Linux window-state events still come
from AT-SPI; EWMH and Sway state changes without a corresponding AT-SPI event
must be observed by reading a new snapshot.

#### Why uinput instead of libei + portal RemoteDesktop?

`org.freedesktop.portal.RemoteDesktop` (libei) is the architecturally "correct" Wayland input-sim path and the future of structured input injection on Linux, but today it covers a strict subset of the ecosystem: only `xdg-desktop-portal-gnome` and `xdg-desktop-portal-kde` support it, and neither has a usable headless mode without a session manager (GDM / SDDM). uinput goes through the kernel and is compositor-agnostic, so it works on every Wayland desktop (GNOME, KDE Plasma, sway, Hyprland, Cosmic, weston) and on headless Linux servers, with the same code path. It is the same mechanism `xdotool --using-uinput`, `ydotool`, `wtype`, Steam Input, and Wine all use.

The trade-off is that uinput requires the user to be in the `input` group or to have a udev rule granting `/dev/uinput` access, which grants global input read/write, comparable to macOS Input Monitoring. The portal model is finer-grained (per-app consent) but isn't broadly available yet. xa11y may add a libei backend later as an opt-in upgrade once the portal landscape stabilises.

#### Wayland screenshot portal consent

The Screenshot portal usually auto-approves for non-interactive callers (`interactive=false, modal=false`); xa11y passes both. wlroots compositors via `xdg-desktop-portal-wlr` and GNOME via `xdg-desktop-portal-gnome` both support this.

#### Coordinates and HiDPI

`Element.bounds` and input `Point`s are logical (device-independent) coordinates, matching the cross-platform contract, and `Screenshot.scale` reports the physical-to-logical ratio. The scale is detected best-effort and is exact where it can be read reliably:

- **X11, integer scaling.** Read from `Xft.dpi` in the X `RESOURCE_MANAGER` (the same signal GTK/Qt use). AT-SPI extents and `XTest` are physical, so bounds are divided and input points multiplied by it.
- **Single-output Wayland, integer or fractional.** The exact ratio `physical_mode / logical_size` from `xdg-output` (e.g. `1920 / 1280 = 1.5`), rather than the rounded `wl_output.scale`.

Every other configuration fails closed to `1.0`, so the data is never wrong. There, bounds stay physical and the scale is not upscaled, but capture and input round-trips remain correct because bounds and pixels stay in the same space:

- **Fractional X11.** GTK's X11 window scale is integer-only, so a fractional `Xft.dpi` scales fonts, not the coordinate space.
- **Multi-monitor mixed-DPI Wayland.** A single scalar can't represent per-monitor scales, so it falls back to the largest integer `wl_output.scale`.
- **XWayland in a Wayland session.** Auto selection uses the Wayland screenshot portal and output scale. An explicit screenshot override of `x11` uses the X11 source, which stays `1.0` under XWayland.

`Point` arguments to input simulation, after the logical→physical conversion, are mapped onto the uinput virtual coordinate range. Override the assumed screen size (default 1920×1080) with `XA11Y_SCREEN_WIDTH` / `XA11Y_SCREEN_HEIGHT` env vars if your setup differs.

On Wayland, input simulation refuses pointer actions whose target is an `Element` (`click`, `drag`, `move_to`, `scroll`, and their variants) with an `Unsupported` error. Wayland clients don't know their global position, so the bounds AT-SPI reports are not screen coordinates, and a click computed from them would land somewhere else. Use a semantic action such as `press` or `focus`, or pass a raw screen point. Raw-point pointer actions and keyboard input work as before.

The refusal follows the input backend, not the session. Forcing `XA11Y_LINUX_INPUT_BACKEND=x11` on a Wayland desktop sends input through XWayland and accepts `Element` targets, which land correctly only in X11 (XWayland) applications. Forcing `wayland` on an X11 session refuses them.

### GTK press fallback (Linux)

GTK 4 menu-button widgets (`GtkMenuButton`, `AdwMenuButton`, `AdwSplitButton`) present as an outer `push button` accessible that advertises `NActions = 0` wrapping an inner `toggle button` that carries the real `click` action. Calling `press()` on the outer would normally raise `ActionNotSupported`. When the owning application identifies itself as GTK via `Application.ToolkitName == "GTK"`, xa11y-linux instead walks a bounded slice of the outer's subtree (BFS, depth 3, restricted to roles that carry a click action, name must match) and invokes the single matching descendant it finds. Scoping is strict. It only runs inside GTK apps, only when the widget's own Action interface is empty, and only when exactly one candidate matches. Ambiguous subtrees still surface the original error.

### WebKitGTK tables

Two WebKitGTK behaviors affect `<table>` content (verified against WebKitGTK 2.52; both are engine behaviors, not xa11y ones):

- **`<th>` cells can destabilize the whole page's tree.** With a window manager present, a table containing `<th>` header cells can send WebKit's accessibility tree into continuous invalidation churn. Every content accessible goes defunct moments after being exposed, and the page effectively vanishes from AT-SPI. If a WebKitGTK-based app's tree keeps coming back empty or `unknown`, check for this (xa11y marks dead objects with `raw["atspi_defunct"]`).
- **Layout-table heuristic.** A `<table>` without headers or a `<caption>` is judged decorative and dropped from the accessibility tree entirely. Cell text is exposed through the AT-SPI Text interface (surfaced as the cell's `value`) rather than as the accessible name, so use `table_cell[value*="..."]` selectors for WebKitGTK content.

### Linux Electron and Chromium apps

On Linux, Electron and Chromium-based apps have their AT-SPI2 bridge disabled by default for performance. xa11y will connect to the app but its tree will contain only the top-level window, so `App.by_name("…").locator("button").count()` returns 0 even though buttons are visible on screen.

To expose the full tree, launch the app with `--force-renderer-accessibility`:

```bash
# VS Code
code --force-renderer-accessibility

# Cursor
cursor --force-renderer-accessibility

# Google Chrome / Chromium
google-chrome --force-renderer-accessibility
```

In a session with no settings daemon (CI, Xvfb, a container), also set `ACCESSIBILITY_ENABLED=1` in the app's environment. There, Chromium needs both the variable and the flag before it exposes web content.

Representative node counts on Ubuntu 24.04 + GNOME 46 (Wayland):

| App       | Without flag | With flag |
| --------- | ------------:| ---------:|
| VS Code   | 1            | 140       |
| Cursor    | 1            | 116       |
| Chrome    | 1            | 210       |

Native GTK apps (Nautilus, gnome-terminal, GNOME Calculator, gnome-text-editor) don't need the flag, because their AT-SPI2 bridge is enabled by default.

Firefox exposes its tree when launched with `MOZ_ACCESSIBILITY_ATK2=1` set in the environment.

To diagnose whether a target app has AT-SPI2 enabled at all:

```bash
busctl --user tree org.a11y.atspi.Registry | grep -i "<app-name>"
```

If the app's subtree is missing, the problem is the app's accessibility configuration, not xa11y.
