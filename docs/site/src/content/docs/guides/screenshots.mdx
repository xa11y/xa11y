xa11y can capture pixel-level snapshots of the screen alongside its accessibility APIs. This is useful for attaching screenshots to test failures, feeding vision-language models with the same frame the agent is reasoning about, or visually diffing a region around a specific control.

The entry points are:

- **Full screen** captures whatever the platform treats as the whole screen. On Windows that is the virtual desktop, which spans every monitor. macOS captures one display. Linux captures the X11 root window or the Wayland portal's desktop image.
- **Region** captures an explicit rectangle in logical screen coordinates.
- **Element** captures the pixels under an accessibility element's current bounds.

Screenshots are decoupled from the accessibility and input layers. Capture never raises or activates the target window. Whatever pixels sit at the requested coordinates are returned, including any occluding windows. Bring the target to the foreground yourself if you need a clean capture.

## Permissions

| Platform | Requirement |
| --- | --- |
| macOS | Screen & System Audio Recording for the terminal/IDE |
| Windows | None for normal user sessions |
| Linux (X11) | `DISPLAY` set to a reachable X server |
| Linux (Wayland) | `xdg-desktop-portal` with screenshot support (user consent dialog may appear) |

## Working with the pixel buffer

A `Screenshot` carries raw RGBA8 pixels, dimensions, a compatibility scale,
and the mapping frozen when the pixels were captured. `width` and `height`
always describe the **actual returned image**, including a crop or resize,
and `pixels.len()` equals `width * height * 4`. `scale` remains useful for old
single-display code, but one scalar cannot describe a mixed-DPI desktop or a
non-uniform resize. Use `desktop_to_image` / `image_to_desktop` for points and
`desktop_rect_to_image` for rectangles. JavaScript uses `desktopToImage`,
`imageToDesktop`, and `desktopRectToImage`. A rectangle
that crosses displays can produce multiple image rectangles.

The conversion methods fail explicitly when mapping is unavailable (for
example, a Rust `Screenshot::new` built from arbitrary pixels). On Windows
they also reject a capture after the display layout or DPI arrangement has
changed; capture a fresh image before using one of its pixels as an input
target. This does not detect an ordinary app or window moving.

<Tabs syncKey="lang">
  <TabItem label="Rust">
    ```rust
    let shot = screenshot()?;
    println!("{} x {} @ {}x", shot.width, shot.height, shot.scale);

    // Encode as PNG bytes (e.g. to upload or embed)
    let png_bytes: Vec<u8> = shot.to_png()?;

    // Or write directly to disk
    shot.save_png("out.png")?;

    // Raw RGBA for custom processing
    let rgba: &[u8] = &shot.pixels;

    // Pixel in this exact image -> desktop point suitable for input.
    let target = shot.image_to_desktop(Point::new(20, 30))?;

    // Cropping and resizing carry the mapping forward.
    let thumbnail = shot.crop(Rect { x: 0, y: 0, width: 800, height: 600 })?
        .resize(400, 300)?;
    ```

## Migrating from v0.14

Code that treated `Screenshot.scale` as a universal desktop-to-image multiplier
should use `desktop_to_image`, `image_to_desktop`, and
`desktop_rect_to_image` instead. A single scale cannot represent a capture that
crosses displays with different DPI settings. Captured screenshots now retain
the exact mapping that produced their pixels, and `crop` and `resize` carry
that mapping forward. `scale` remains for compatibility and describes the
primary capture scale only.

On Windows, desktop bounds remain in logical coordinates and preserve their
desktop origin. Full-screen image dimensions are the actual returned pixel
dimensions, so they can differ from the logical desktop extent. Right and
bottom input anchors select the last point inside the element's half-open
bounds rather than the first point outside it.

## Example: screenshot on test failure

A common pattern is to capture the full screen (or the app under test) whenever an assertion fails, and attach it to the test report.

<Tabs syncKey="lang">
  <TabItem label="Rust">
    ```rust
    fn capture_on_fail(name: &str, test: impl FnOnce() -> Result<()>) -> Result<()> {
        match test() {
            Ok(()) => Ok(()),
            Err(e) => {
                if let Ok(shot) = screenshot() {
                    let _ = shot.save_png(format!("target/failures/{name}.png"));
                }
                Err(e)
            }
        }
    }
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    import pytest

    @pytest.hookimpl(hookwrapper=True)
    def pytest_runtest_makereport(item, call):
        outcome = yield
        report = outcome.get_result()
        if report.when == "call" and report.failed:
            try:
                xa11y.screenshot().save_png(f"artifacts/{item.name}.png")
            except xa11y.XA11yError:
                pass
    ```
  </TabItem>
  <TabItem label="JavaScript">
    ```js
    import { screenshot } from '@crowecawcaw/xa11y';

    afterEach(async function () {
      if (this.currentTest?.state === 'failed') {
        try {
          const shot = await screenshot();
          await shot.savePng(`artifacts/${this.currentTest.title}.png`);
        } catch { /* capture failure shouldn't mask the test failure */ }
      }
    });
    ```
  </TabItem>
</Tabs>

## Error handling

Capture raises four of xa11y's error variants:

- `PermissionDenied` when macOS Screen Recording is not granted, or the Wayland portal denied consent.
- `Unsupported` when no capture backend covers the session, which a missing `DISPLAY` or an unresponsive Wayland portal will both produce.
- `NoElementBounds` when the element passed to `screenshot_element` has no bounds.
- `Platform` for a raw OS or FFI failure during capture or PNG encode.

The Python example above catches `xa11y.XA11yError`, which covers
`PermissionDenied`, `Unsupported`, and `Platform`. `NoElementBounds` surfaces
as a plain `ValueError` in Python, so catch that too when capturing by element.
See [Errors](/reference/errors/) for the full mapping.
